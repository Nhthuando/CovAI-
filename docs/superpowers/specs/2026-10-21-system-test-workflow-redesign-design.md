# System Test workflow redesign — design contract

Date: 2026-10-21. Status: proposed for owner review. This document is a design, not an implementation claim.

## Authority and scope

- The supplied `Chi_tiet_System_Test.png` is the business workflow. The owner confirmed that it takes precedence where it differs from Figma.
- [CovAI — System Test Workflow Redesign](https://www.figma.com/design/8CiK65mRXGvo0N2vTqGQ19/CovAI-%E2%80%94-System-Test-Workflow-Redesign?node-id=0-1) is the visual contract. It shows no-tests, scenario library, live run, results, coverage/gaps, and three live detail variants. Sample counts, paths, percentages and dates in the mockups are illustrative.
- This change covers System Test in the existing project/snapshot workspace. Unit and Integration Test behavior stays in its current routes.
- The measured workflow uses Playwright first. Existing Cypress execution remains available with explicit unsupported labels for evidence it cannot produce.

## User outcome

A project owner can enter a business brief, reuse or create scenarios, inspect each scenario's Input and Expected, approve the suite, run it against an isolated application, inspect scenario-specific evidence, distinguish app failure from a weak test, find uncovered behavior, approve additional scenarios, compare coverage before/after and export a traceable PDF report.

## Workflow and state gates

1. **Context.** Store a versioned business brief and criterion list for the snapshot. The form accepts project purpose, actors, main flows, preconditions, test data constraints and expected outcomes. An AI extraction or source discovery produces a draft only. The owner confirms criteria; its revision/hash is preserved.
2. **Discovery.** Scan Playwright/Cypress files before any run, including titles and source locations where statically supported. If no files exist, show the three Figma actions: write a scenario, generate from brief, import a spec. A candidate generated by AI is a draft, not automatically executable or a verified requirement.
3. **Scenario library.** Merge confirmed criteria with discovered or authored scenarios. Every executable scenario has stable ID, file/source location, flow, input/precondition, expected observable outcomes, assertion mapping, provenance, scope and review state. Show unsupported dynamic/custom-fixture parsing as `NEEDS_REVIEW` instead of inventing fields. Compare criterion IDs with scenario/assertion bindings; show missing coverage as a review finding.
4. **Review.** The owner may edit/add Input and Expected and inspect a diff of the underlying test. Saving a reviewed scenario records approver, time, criterion revision, source/test hash and assertion site hashes. Any change to those inputs invalidates review. The **Run after review** action is disabled for unresolved review blockers; it shows the exact scenario and reason. Non-blocking source gaps remain visible.
5. **Execution.** Queue an owned, snapshot-scoped run. Prepare a disposable AUT workspace and isolated test data/database. Run the approved Playwright suite without mock API routing in Full Stack mode. Preserve the existing assessment identity, lease, cancellation and two independent runs. Publish bounded live events for run/scenario/step transitions, with a browser preview and code/API/data evidence only where an adapter actually captured it. Pause means stop scheduling the next scenario at a safe boundary; it does not freeze a running Playwright action. Stop cancels the owned job and labels unfinished scenarios `CANCELED`.
6. **Verdict.** `PASS` means reviewed expected assertions passed in the required run(s); it is never inferred from a screenshot or process exit alone. `FAIL` preserves the original test, actual assertion/error, trace, screenshot, sanitized network evidence and source revision. `WEAK` is separate from execution: a passing scenario with absent/unsupported outcome assertions, an observed repeat inconsistency, or an explicitly supported quality rule is flagged with reason and evidence. A pass on retry does not erase the first failure. Infra/setup faults are `BLOCKED`, not application bugs.
7. **Gap analysis.** Report measured frontend and backend coverage separately, with numerator, denominator, scope, run identity and status. Report business criterion coverage separately from line/branch coverage. Findings distinguish failed behavior, weak assertion, missing criterion/flow and unexecuted code. An unexecuted branch alone is a candidate gap, not proof of a missing business scenario. Prioritize proposals by confirmed criterion, observed failure and measured uncovered branch, and show source references.
8. **Improvement loop.** The user or AI proposes one or more new scenarios tied to specific finding IDs. The proposal must preserve the existing suite and pass static safety checks; validate in disposable runs with no regressions. Present code and Input/Expected for explicit owner review. Apply only an exact hash-matching approved proposal, then publish a new assessment. A proposal closing a confirmed missing criterion may be accepted without a source-coverage increase when the new reviewed assertion verifies that criterion; label the measured coverage delta as zero. A proposal whose only claim is source-coverage improvement still requires a comparable measured increase. Keep the previous report and before/after measurements; never delete a failing test because it reveals a bug.
9. **Dashboard and report.** Results show counts by distinct verdict, repeat stability, measured coverage with before/after where comparable, criterion coverage, gaps, evidence and limitations. A diagnostic quality score is shown only when confirmed criteria, supported assertion analysis, independent run evidence and an artifact manifest are present. Its fixed 100-point rubric is: verified criteria 40, reviewed scenarios with supported outcome assertions 25, clean independent-run stability 20, and captured required artifacts 15. The required-artifact set is one approved checkpoint or final screenshot per executed scenario plus trace and failure screenshot for each failed scenario. Each component and denominator is visible; absent manifest or unsupported assertion analysis makes the total `NOT_CALCULATED`, while a missing individual artifact reduces its component. The score is a transparent test-suite heuristic, never a correctness probability. Export an immutable server-generated PDF for a selected completed assessment, containing snapshot/source/test/revision hashes, run IDs and time, scope, verdicts, actual vs expected, evidence links/hashes, findings, coverage counters, quality-score breakdown and unsupported sections.

## UI contract

The main System Test view follows Figma's three tabs: **Scenarios**, **Live run**, **Results**. **Coverage & gaps** is entered from Results. The scenario library uses a left list and right detail panel with Flow, Input, Expected and review status. The no-tests state exposes write, AI generate and import. The live view shows the current browser, step list and detail tabs for Code paths, Data & DB and API calls. Empty/unsupported evidence is labeled, not filled with examples. Results show failures and weak tests first, then passed scenarios; a failure detail displays Expected, Actual, screenshot, steps, network and trace. Coverage/gaps shows frontend lines, backend branches, repeat stability and next action. Desktop composition follows Figma; narrow layouts stack panes and preserve keyboard access and readable evidence.

The business brief and review controls are additional workflow surfaces required by the diagram, even though they are absent from the Figma frames. They should use the same dark visual language and design tokens. The Figma `Pause` control uses the safe-boundary meaning above.

## Module boundaries

- **Brief and criteria**: versioned owner-confirmed requirement model. It does not infer correctness from source alone.
- **Scenario catalog**: imported/discovered/handwritten/AI-draft scenario identity and review metadata, independent of `TestScenario` (which currently represents executed results).
- **Assessment orchestrator**: admission, snapshot identity, disposable setup, two independent runs, cancellation and persistence. Extend the current implementation rather than replacing its proven measurement contract.
- **Live evidence adapter**: Playwright reporter/fixture emits stable run/scenario/step IDs, bounded screenshots, response metadata and optional request correlation. It never exposes raw secrets or arbitrary AUT responses. Ordered sequence and cursor allow recovery after reconnect. Live transport failure does not alter test results.
- **Evidence storage**: immutable manifest and bounded artifacts keyed by assessment/run/scenario. Store hashes, paths and retention metadata in DB; serve only after snapshot ownership checks. Invalid or truncated evidence has an explicit status.
- **Coverage and quality analysis**: existing Istanbul measurement remains the source for aggregate code coverage. Scenario-specific code-path claims require isolated per-scenario measurement or a verified correlation adapter; aggregate hits must never be attributed to one scenario. Requirement verification keeps approved assertion bindings and repeat-run proof. DB changes require an explicit allowlisted test-data adapter; absent adapter means `NOT_CAPTURED`.
- **Proposal service**: preserve previous test text, verify candidate in isolation, require owner approval, compare identical source/scope/runtime identities and publish atomically.
- **Report service**: renders the persisted assessment and evidence manifest through PDFKit, with ownership and snapshot identity checks.

## Data and API changes

Additive schema changes are expected for a business brief/revision, scenario catalog/review state, run event cursor and evidence manifest. Keep current `SystemRequirementRevision`, `SystemAssertionBinding`, `SystemTestAssessment`, `TestRun`, `TestScenario` and proposal history; migrate or link rather than overwrite. A draft scenario and an execution result must remain separate records. Exact migration SQL and cascade effects require review before applying.

Extend the authenticated `/api/coverage/:snapshotId/system` routes with: brief revision create/confirm; catalog list/create/import/update/review; run admission by approved revision; run events with cursor; scenario evidence manifest/artifacts; proposal review/apply; and PDF download by assessment ID. All reads and writes verify snapshot ownership through `req.user.id`. The route contract includes explicit `DRAFT`, `REVIEWED`, `STALE`, `BLOCKED`, `RUNNING`, `COMPLETED`, `CANCELED` states and `UNSUPPORTED`/`NOT_CAPTURED` evidence statuses. Mutations require expected revision/hash for optimistic concurrency.

## Evidence and safety rules

- Preserve raw Playwright results/traces and source/test hashes. Capture API method, normalized path, status and duration; allowlist response fields only when explicitly configured. Redact authorization, cookie, token, password, API key, query secrets and sensitive DOM/local storage values before persistence or broadcast.
- A browser request is correlated to a backend route only through a verified request/trace ID or instrumentation event. AST route maps alone are hints and cannot be shown as executed paths.
- Database tables/rows are shown only from an isolated test database and an allowlisted adapter. Never run live test writes against a user's production database.
- Coverage remains `MEASURED`, `PARTIAL`, `NOT_MEASURED`, `UNSUPPORTED` or `INVALID` with provenance. The PDF and UI use the same persisted calculation. A 0 denominator yields no percentage.
- Generated tests are untrusted drafts; static validation, execution and owner review are distinct gates. Proposed tests never replace existing failing tests automatically.
- Artifact limits cover size, count, retention and path containment. Support disconnect/reload by replaying persisted events, not by trusting a Socket.IO message as the sole record.

## Acceptance criteria

1. Zero-test, existing-test and unsupported-test snapshots show truthful discovery states before a run.
2. The user can create/confirm a brief, review each scenario's Input/Expected and see which confirmed criteria remain unbound. A changed requirement, test file or assertion invalidates the matching review.
3. Full Stack Playwright runs only after review, uses isolated AUT/test data, and emits scenario/step events whose final states reconcile with the stored Playwright result. Reconnect resumes from a cursor. Pause/stop semantics match the UI text.
4. PASS/FAIL/WEAK/BLOCKED/CANCELED and MISSING findings are derived from documented evidence rules. A failed assertion retains its test, expected/actual, trace and screenshot. Missing artifacts are labeled unavailable.
5. Coverage numbers come from the existing measured contract, include denominator/scope and are not invented per scenario. Repeat stability uses independent runs with retries disabled for that measurement.
6. The AI loop presents a source and test diff, verifies without regression, requires approval for new expected outcomes, and rejects stale hashes. A confirmed missing criterion may be closed with reviewed assertion evidence even when source coverage does not rise; a coverage-only improvement requires a measured increase. Before/after comparisons are shown only when source, scope, runtime and denominators match.
7. The diagnostic quality score shows all four components and is absent rather than estimated if confirmed requirements, supported assertion analysis or repeat-run evidence is missing.
8. The selected assessment exports a PDF whose counts, hashes and findings match its persisted API response. Another project's user receives 404 for all records and artifacts.
9. Existing Playwright/Cypress result endpoints and Unit/Integration views continue to work. Cypress evidence limitations are explicit.

## Implementation constraints

- Add only the Prisma records needed for brief revision, durable scenario catalog, review, sequenced live events and artifact manifest; retain existing assessment and result tables. Review every cascade in migration SQL against historical reports.
- Use Playwright reporter events for durable run/scenario/step progress. For the browser preview use bounded screenshots taken by the managed fixture; a screencast may be enabled only after a verified runtime compatibility and cost test. The preview is informative and does not decide PASS/FAIL.
- Database change evidence is opt-in through an allowlisted adapter against the disposable database. PostgreSQL/MySQL adapters may be implemented as separate steps; until a verified adapter exists, the Data & DB tab says `NOT_CAPTURED`.
- Unsupported custom Playwright fixtures and dynamic test definitions remain runnable through the legacy path, but cannot receive inferred Input/Expected or reviewed assertion status. Managed execution requires explicit manual catalog metadata and an executable proof of assertion mapping; otherwise the run gate names the unsupported feature.
